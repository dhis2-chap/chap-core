    Chap Projects¶

    A Chap project is a directory that holds a model choice, a dataset, the configuration files and the results of evaluating it. Inside a project, chap eval runs without any options.

    Create a project¶

    chap init creates the project directory:

    chap init --help

    chap init laos --model builtin:seasonal_median --dataset ./example_data/laos_subset.csv
cd laos
chap validate
chap eval

    chap validate checks the dataset against the model, including that masked ranges end before the project's evaluation window, and chap eval runs the backtest. chap eval warns about the problems chap validate reports as errors and runs anyway; chap eval --strict (or strict: true in chap.yaml) stops on them instead. chap sanity-check-model trains the model once on the project's dataset and makes two forecasts, which is a quick check that it runs at all. Each chap eval writes a new NetCDF file and an HTML plot to output/, named after the model and the time of the run, so you can compare runs afterwards:

    chap export-metrics --input-files output/*.nc --output-file metrics.csv

    Chap commands use the chap.yaml in the current directory, so run them in the project directory, not in input/ or output/. A chap.yaml in any other directory, such as a parent or your home directory, never changes a command, and a chap.yaml owned by another user is ignored.

    chap init laos creates the directory laos if it does not exist. Without a directory, chap init asks before making the current directory the project, for example a directory that already holds your data or your model's code; --yes (-y) skips the question, and so does naming the directory, as in chap init .. In both cases an existing chap.yaml is only replaced with --force.

    chap init loads the model once to check that it can be found and to read its options, and loads the dataset with its column mapping and data settings to check that they fit together. Nothing is written when a check fails. A local model directory inside the project or next to it is stored in chap.yaml relative to the project, so the two can be moved together. A model directory further away is stored as an absolute path.

    A GitHub model is pinned to the commit its default branch points at when you run chap init, written as https://github.com/org/model@<commit>. Every run then uses the same model code, so results in output/ stay comparable. Use --no-pin to have each run use the latest commit instead, or edit the commit in chap.yaml to move to a newer version.

    Chap Marketplace models¶

    --model also takes the ID of a model in Chap Marketplace. chap init looks up the model's verified stable version and stores its container image:

    chap init study --model chapkit_ghr_model --dataset ./data.csv

    This writes model_name: docker://ghcr.io/chap-models/chapkit_ghr_model:sha-<commit>@sha256:<digest> to chap.yaml. The digest is the one Chap Marketplace verified for that version, so the project keeps running the same image even if the tag is later moved. The image is run as described for docker:// images below.

    Chapkit models¶

    chap init takes the same --run-config options as chap eval and stores the ones you give in chap.yaml, so every later command runs the model the same way:

    # A chapkit model in a local directory, started and stopped by each command
chap init study --model ../chapkit_minimalist_example_py --run-config.is-chapkit-model

# An MLproject model served as a chapkit service for the duration of each run
chap init study --model https://github.com/chap-models/mlproject_template_python --run-config.as-chapkit

# A chapkit container image, such as a Chap Marketplace model, run as a container by each command
chap init study --model docker://ghcr.io/chap-models/chapkit_ghr_model:sha-84fbe77

# A chapkit service that is already running
chap init study --model http://localhost:8000

    For a chapkit service, input/model_config.yaml is filled with the options the service declares.

    A docker:// image needs Docker. Each command pulls the image if it is missing, runs it on a free local port and removes the container afterwards, also when the command is interrupted with Ctrl-C, stopped with kill or its terminal is closed. Only kill -9 leaves the container running; find it with docker ps --filter name=chap- and remove it with docker rm -f <name>. An image with no build for your machine, such as an amd64-only image on Apple Silicon, runs under emulation, which makes it slower.

    Project layout¶

    Path Contents
    chap.yaml The model and evaluation settings. Marks the project root.
    input/data.csv The dataset, copied in by chap init --dataset.
    input/data.geojson Region polygons, copied in when found next to the dataset.
    input/data_settings.yaml Data settings such as masked ranges, as for --data-configuration. chap init writes a commented example that sets nothing until you edit it.
    input/column_mapping.json Optional covariate-to-column mapping, as for --data-source-mapping.
    input/model_config.yaml The model's options. chap init --model writes it with the model's default values when the model has options, with each option's description and allowed values as comments.
    output/ Evaluation results.
    .chap/ Chap's working copies of the model, one per run, in place of runs/. Listed in .gitignore.

    chap init --data-settings, --column-mapping and --model-config copy existing files to these names. --model-config may only set options the model has. You can also add or edit the files by hand: a file in input/ is used whenever it exists.

    chap init --force keeps data_settings.yaml and column_mapping.json. When it is given a new dataset, it checks that the kept files still fit it, and stops if they do not.

    chap.yaml¶

    Every key in chap.yaml is a command-line option, with the leading -- dropped and dashes written as underscores. Nested options such as --backtest-params.n-periods become nested keys:

    model_name: builtin:seasonal_median

eval:
  backtest_params:
    n_periods: 3
    n_splits: 7
  plot: true

    Top-level keys apply to every command that takes them. A section named after a command, such as eval:, applies to that command only. Relative paths are relative to the project root, so dataset_csv: ../shared/vietnam.csv uses a dataset outside the project instead of input/data.csv.

    A misspelled option inside a known option or a command section, such as backtest_params: {n_period: 3}, stops the command with an error, and so does a single value where options are expected, such as run_config: true or model: builtin:global_median (model: is the section for chap model schema; the model is model_name). A top-level key that no project command takes gives a warning.

    Which value is used¶

    For each option, the first of these that gives a value wins:

    1. The option on the command line.
    2. The command's section in chap.yaml.
    3. A top-level key in chap.yaml.
    4. The matching file in input/.
    5. Project defaults: a new file in output/ for --output-file, .chap/runs for --run-config.runs-dir, and for chap validate, the backtest_params of the eval: section.
    6. The command's own default.

    So chap eval --backtest-params.n-periods 6 changes the forecast horizon for one run and leaves the project unchanged.

    The files in input/ belong to the project's own dataset and model. When --dataset-csv is given on the command line, or dataset_csv in chap.yaml points at another file, data_settings.yaml and column_mapping.json are not used, and when --model-name is given, model_config.yaml and the is_chapkit_model and as_chapkit run options in chap.yaml are not used. This keeps masked ranges or model options written for the project from being applied to another dataset or model.

    Each run logs the project it uses and where each value came from.

    Commands that use the project¶

    chap eval, chap validate, chap model schema and chap sanity-check-model take their options from the project. Other commands work as they do outside a project.
